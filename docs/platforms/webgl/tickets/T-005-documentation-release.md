## もし一から作り直すなら

**ドキュメント構成**:
セットアップガイド（SETUP.md）への追記と独立ドキュメント（JAPANESE_INPUT.md）の併存は正しい判断。ユーザーは「WebGL でどう動かすか」を SETUP.md 一箇所で完結させたく、「なぜ WebGLInput なのか・他候補との比較」は技術背景として分離したい。ただし両者のリンクが一方向（SETUP→JAPANESE_INPUT）になりがちで、JAPANESE_INPUT.md から SETUP.md の該当セクションへの逆リンクも張るべきだった。

**調査・チケットの扱い**:
`JAPANESE_INPUT.md` の調査セクション（問題分析・動作原理・他候補比較）は恒久保存、マイルストーン/チケットセクションは完了後に `docs/archive/` か PR 本文へ移動するのが理想。T-001〜T-005 のチケットファイルは「なぜこの設計にしたか」の判断根拠が詰まっているため削除せず、`tickets/` をそのまま読み物として残す（ステータスのみ完了に更新）方針が最もコストパフォーマンスが良い。

**設計思想**:
uPiper には既に CHANGELOG.md が存在し、ユーザー向けリリース情報はそこで一元管理される。したがって WebGL 日本語入力対応のドキュメントは「セットアップガイドへの最小追記＋既存調査ドキュメントの完了マーク」で十分で、新規 RELEASE_NOTES 等を追加する必要はない。包括的な独立ドキュメントを量産するより、既存構造の延長線上で追記する方が保守負債が小さい。

**やり直すなら変えること**:
1. T-005 を 1 PR に集約せず、「ドキュメント更新 PR」と「チケットステータス整理 PR」に分割（レビュー容易性向上）
2. SETUP.md の日本語入力セクションに「WebGLInput バージョン更新手順」を小節として含める（T-005 懸念事項で挙がっていた未決課題）
3. CHANGELOG.md への WebGL IME 項目追加を T-005 の必須タスクに含める（現行チケットでは未明記）

**今回のアプローチを維持する理由**:
feature ブランチは既に 5 チケット分の変更を含み、分割しても develop へのマージは結局 1 回。PR 粒度を細分化するよりも、1 PR でレビュアーに全体像を見せる方がレビュー工数とマージ順序の管理コストが下がる。また `pr-target-check.yml` による feature→develop→main 強制フローの下では、feature ブランチ単位で PR をまとめる現行運用と整合する。
