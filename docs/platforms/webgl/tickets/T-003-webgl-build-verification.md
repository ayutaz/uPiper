## タスク目的とゴール

WebGLビルドで日本語IME入力から音声合成までのE2Eフローが複数ブラウザで正常動作することを検証し、品質基準を満たすことを確認する。

**ゴール**: InferenceEngineDemoのWebGLビルドにおいて、WebGLInput経由の日本語IME入力 → MultilingualPhonemizer → PuaTokenMapper → PhonemeEncoder → ONNX推論 → AudioClip再生の一連のパイプラインが、必須ブラウザ（Chrome/Firefox/Edge）で安定して動作することを検証する。コード変更は検証中に発見された問題の修正のみをスコープとする。

## 実装する内容の詳細

このチケットは主に検証タスクであり、コード変更は検証で問題が発見された場合の修正に限定する。

### 1. 検証シナリオ

以下の手順でE2Eフローを検証する:

1. WebGLビルド実行（InferenceBackend.Auto）
2. ブラウザでデモページを開く
3. WebGLInteractionGateのクリック待機 → AudioContext再開を確認
4. InputFieldにフォーカス → HTML input要素がオーバーレイ表示されることを確認
5. 日本語IMEで「こんにちは」を入力（変換 → 確定）
6. `_inputField.text`に「こんにちは」が反映されることを確認
7. 生成ボタン押下 → 音声合成完了 → AudioClip再生

### 2. ブラウザマトリクス

| ブラウザ | バージョン | Graphics API | 推論バックエンド | テスト優先度 |
|---------|-----------|-------------|----------------|------------|
| Chrome | 90+ | WebGL2 | GPUPixel | 必須 |
| Chrome | 113+ | WebGPU | GPUCompute | 推奨 |
| Firefox | 89+ | WebGL2 | GPUPixel | 必須 |
| Edge | 90+ | WebGL2 | GPUPixel | 必須 |
| Safari | 15+ | WebGL2 | GPUPixel | 任意 |

### 4. 潜在的な修正箇所（検証で問題発見時）

検証中に以下の問題が見つかった場合、このチケット内で修正する:

## 懸念事項とレビュー項目

### 懸念事項

- **IME変換候補ウィンドウの位置**: 表示位置がブラウザ/OSの組み合わせごとに異なるため、全環境での統一的な動作保証は困難
- **フルスクリーンモード**: HTML input要素の位置ずれが発生する可能性がある（WebGLInput既知問題 #191）
- **WebGPU + IME入力の同時動作**: WebGPU環境でGPUCompute推論とIME入力ハンドリングの間に競合が発生しないか確認が必要
- **モバイルブラウザ**: ソフトキーボード表示時のビューポート変更がUnity Canvas レイアウトに影響する可能性がある

### レビュー項目

- [ ] 全必須ブラウザ（Chrome/Firefox/Edge）でテスト完了
- [ ] 日本語IME E2Eフロー（入力 → 合成 → 再生）成功
- [ ] 既存の英語入力に退行なし
- [ ] ブラウザコンソールにエラー/警告なし

## もし一から作り直すなら

**テスト自動化戦略**:
手動テストの限界は「再現性」「回帰検知の遅さ」「ブラウザ/OS組み合わせ爆発」の3点に集約される。一からやり直すなら、WebGLビルドに対するE2Eテストを3層に分離する: (1) Unity側で `[UnityTest]` + WebGLプレイヤー相当のモックで動作する「ビルド非依存のロジック層テスト」、(2) Playwright + ヘッドレスChromiumで実WebGLビルドをロードする「ブラウザ層スモークテスト」、(3) 手動のIME/UX確認を残す「ヒューマンテスト層」。IME入力はOS依存で自動化困難なため、テスト用に `TestHarness.InjectText(string)` のような非UI経路をWebGLビルドに組み込み、IMEを迂回してパイプライン自体を検証する。

**CI統合テスト**:
deploy-webgl.yml のビルド成果物を artifact 化し、別ジョブで `npx playwright test` を走らせる構成。テストは「ビルドがロードされる」「AudioContextが初期化される」「TestHarness経由で日本語/英語/中国語の合成が成功しPCM長が閾値超」をアサート。スクリーンショット比較ではなく、波形ハッシュ/RMS値のゴールデン比較で決定論性を担保する。WebGPUパスはChromium flag、WebGL2パスはFirefox、の2ブラウザをマトリクス実行。

**設計思想**:
TTSの本質価値は「音が出ること」であり、ピクセル一致ではない。ROI最大化のため、ビジュアル回帰よりも「パイプラインが壊れていないこと」を低コストで継続検証することに投資する。

**やり直すなら変えること**:
1. WebGLビルドに `?testMode=1` 相当のテストハーネスを最初から組み込む
2. 波形ゴールデン値を Git LFS で管理し、モデル更新時のみ再生成
3. ブラウザ互換マトリクスを CI ラベル駆動（`[webgl-full]`）で限定実行しコスト最適化

**今回のアプローチを維持する理由**:
Unity WebGLビルドは10分超のビルド時間と数百MBの成果物を要し、CI上での毎PR実行はコスト面で非現実的。また現状ユーザー規模ではIME経路の細かな差異が優先度を持たず、リリース前の手動スモークテストで十分にリスクを抑制できる。自動化投資は利用実績と不具合頻度が積み上がってから段階的に行う方が合理的。
